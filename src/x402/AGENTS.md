# Guarded HTTP payments contract

## Purpose
Provide resource-bound guarded HTTP payments, durable budgets and compatible merchant verification.

## Ownership
Own src/x402 and src/__tests__/payment*.test.ts payment regressions. The root owns shared AgentWallet/execution, package exports, deployment evidence, and release policy. Read root and src contracts before edits.

## Local Contracts
X402Client(wallet, config = {}) defaults to autoPay false. Every request requires an approved HTTPS origin; automatic payment requires exact recipient, ERC20 asset, wallet-bound eip155 chain, explicit positive bigint per-request/daily limits and explicit service budgets. One client handles one asset; accounting is scoped to vault/chain/asset. Multiple assets need separate clients and explicit per-asset caps. GET and HEAD are the only replayable methods. Caller payment proofs, credentials in URLs, fragments, all redirects and mismatched response resources are rejected. createX402Fetch and wrapWithX402 preserve Request details and use the actual supplied fetch without swapping global state. The default transport resolves all DNS answers, rejects any non-public address and pins the validated address into the actual TLS request. It requires port 443, refuses redirects/compression, bounds headers to 32 KiB, body to 1 MiB and the entire request/DNS deadline to five seconds, and propagates caller abort. Owner-supplied fetchFn is an explicit trusted alternate transport and must uphold equivalent network controls; the SDK still checks approved origins and response redirects/resources.

Only the custom agent-vault-tx-v1 scheme is supported. Its challenge uses AGENT-VAULT-PAYMENT-REQUIRED and its proof uses AGENT-VAULT-PAYMENT; it does not claim standard x402 interoperability. Standard exact EVM x402 expects a signature/authorization (EIP-3009 or supported Permit2 flow), not a transaction hash; the guarded account has no validated standard authorization integration. Abstract delegated-facilitator signing is unverified and disabled; no default facilitator or token claims remain.

Challenges are bounded base64 JSON headers with exact resource, recipient, asset and chain, positive uint256 decimal amount, unique 16–128-character requestId, required integer confirmations from 1–64, expiresAt as the latest mining timestamp within five minutes, and a separate required proofExpiresAt. The proof window after expiresAt must allow at least 30,000 milliseconds per confirmation at max(wallet.confirmations, challenge.confirmations), and at most 86,400,000 milliseconds. This is a conservative admissibility policy, not a chain finality guarantee; timing/provider uncertainty can still require merchant reconciliation. Malformed or unsupported depth/windows reject before reservation or transfer. A challenge is reserved synchronously before payment-related awaits. Durable request IDs reject replay until proofExpiresAt. executeVaultOperation is the sole asset execution path. The client waits at least max(wallet.confirmations, challenge.confirmations) on the original submitted hash before proof presentation. Receipt success, matching transaction hash and an exact ERC20 Transfer event from vault to approved recipient are required before recording settlement; a queued transaction is not a payment. The gas operator then signs an EIP-712 binding to transaction hash, exact resource, requestId, token, recipient, amount, confirmations, expiresAt and proofExpiresAt under the vault/chain domain. Legacy custom challenges or signatures missing the new fields fail closed.

Known submission hashes are captured before the durable onSubmitted write and from the execution result. Later transfer-evidence, accounting, binding-signature, transport or response-validation failures throw the exported X402SubmittedPaymentError, which extends SubmittedTransactionError and carries txHash, exact resource, requestId, paymentRequirements and the original cause. A known submission requires independent payment/resource reconciliation before requesting another challenge; the error alone does not establish settlement or delivery. Existing SubmittedTransactionError and QueuedTransactionError objects escape unchanged with their recovery fields. Failures without a known hash keep their original error. Neither fetch wrapper releases a submitting reservation, repeats the payment, nor returns a successful response when these steps reject; already completed accounting remains charged.

Every returned paid response carries immutable X402PaymentReceipt facts through getX402PaymentReceipt(response), including txHash, exact resource/requestId, vault, network, asset, recipient and base-unit amount. This is locally verified on-chain settlement with settlement="client-confirmed" and does not certify merchant acceptance or delivery. HTTP status/body/statusText/headers/URL/type/redirected and normal body/clone behavior are preserved, including 402/503 responses; no new challenge is paid automatically. The explicitly custom AGENT-VAULT-PAYMENT-RECEIPT header (PAYMENT_RECEIPT_HEADER) is a base64 JSON informational copy that replaces any merchant-supplied value on paid responses. Trusted reading uses local WeakMap provenance, never header parsing: forged/copied header values give no trusted receipt, changing a returned header does not alter local facts, and SDK response clones retain local receipt provenance. Pre-payment responses are returned unchanged with no local receipt. Callers must inspect HTTP status separately from settlement before any retry.

Receipt/location state uses frozen ECMAScript #private fields. Clones read authoritative receipt facts from the module-private WeakMap and the original private location, ignoring mutable ordinary receipt/location properties supplied by callers. The unexported response subclass still has a publicly reachable constructor, so construction requires an opaque module-private authority token checked before any provenance registration. Borrowed clone calls on unbranded responses reject. Do not use TypeScript-only private fields or public constructor arguments as authority for locally verified payment facts; do not freeze the entire Response/body stream.

getX402PaymentRecovery(outcome: Response | Error) reads immutable X402PaymentRecovery with the original txHash, complete paymentRequirements and optional signed paymentProof retained by this client in this SDK session. retryX402PaymentProof(outcome, init?) uses only that trusted local provenance and exact original resource/transport; it checks the pinned wallet and the same transaction/transfer at the required depth, completes the original reservation once if still pending, signs a binding only if no proof was retained, and sends the exact original proof. It never calls executeVaultOperation, reserves/releases a budget claim, obtains a new challenge, changes the original deadlines or sends a new transfer. GET/HEAD, safe redirects/resources and caller-proof rejection still apply; init may update normal request options such as signal/headers. Concurrent retries deny with the known hash. Paid response clones preserve both settlement and recovery provenance; header mutations/copies and fabricated errors do not confer recovery authority. Already-consumed proofs and protected-resource delivery failures retain their HTTP status and original locally verified hash, requiring merchant incident handling. Expired proof windows reject with the original hash and remain charged. Recovery/proof retention is in-session only; restart/serialized copies need independent operator/merchant reconciliation and unknown reservations remain charged.

## Merchant integration contract
GuardedPaymentMerchant implements the compatible custom verifier. Its strict configuration requires a trusted typed viem PublicClient, vault address, pinned deployed runtime code hash, deployment block, chain ID, recipient, ERC20 asset, exact origin/resource, bigint amount, 1–64 confirmations and merchant-owned durableDirectory. Optional challengeTtlMs is an integer from 1,000–300,000 (default 120,000) and limits latest mining. Optional proofTtlMs is an integer from 30,000 * confirmations through 86,400,000 (default 3,600,000); issueChallenge sets proofExpiresAt = expiresAt + proofTtlMs. The client independently enforces the stronger allowance for its actual max(wallet, merchant) wait depth. Proof windows are bounded delivery opportunities, not guaranteed finality. The PublicClient is trusted chain evidence infrastructure; do not accept an RPC URL or deployment manifest supplied by an untrusted payer. Pin only owner-verified vault/token deployments.

issueChallenge() asynchronously verifies live provider chain, vault code hash and securityVersion at the current block before storing a unique challenge and its minimum future payment block. verifyPayment(base64Header) strictly decodes the canonical custom proof, checks its exact persisted challenge including confirmations and both deadlines, canonical low-S EIP-712 signature against transaction.from, transaction.to against the pinned vault, zero native value, exact canonical agentTransferToken calldata, successful matching receipt with configured confirmation depth, canonical receipt block and timestamp between issuance and expiresAt, historical and current pinned vault code/version, and an actual matching ERC20 Transfer log. Store lookup/consumption remains live only through proofExpiresAt, allowing a timely mined payment to finish confirmation/delivery after mining expires; it never permits late mining. Unknown, queued, reverted, insufficiently confirmed, stale, reorged, malformed and mismatched evidence rejects. RPC evidence checks have a five-second deadline.

Only after every evidence check passes does a synchronous durable atomic transaction consume both request ID and chain-scoped transaction hash globally across every configured resource using the same merchant directory. Concurrent verification/instances can return acceptance only once. Completed identities are never evicted automatically; the 10,000-settlement / 1,000-live-challenge / 4-MiB file bounds fail closed. Corrupt/deleted initialized files, symlinks, unsafe permissions and held/crashed locks reject. Merchant storage must be separate from agent-controlled storage; directory integrity and non-rollbackability remain an owner operational responsibility.

createGuardedPaymentResource(merchant, serveVerifiedPayment) is a framework-neutral GET/HEAD handler that issues the real 402 challenge, verifies the retry and serves the protected resource once. Responses force private/no-store caching; proof failures return 403 and unavailable challenge evidence returns 503. A protected-resource failure after acceptance remains consumed and requires merchant incident handling rather than another automatic payment. createGuardedPaymentHttpsServer(merchant, serve, tlsOptions) provides an opt-in Node HTTPS reference server with bounded headers/request deadlines, no administrative endpoints and no implicit listen/deploy. TLS material remains caller memory. Configure every protected resource with the same trusted durable merchant store for global single-use semantics. The server trusts its configured resource origin, never the incoming Host header.

A public transaction hash alone is insufficient proof. Signature binding and independently read chain evidence are both mandatory. Standard x402 exact still remains unsupported; this implementation and handler speak the explicitly labelled custom protocol.

Primary standard reference: https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md

## Durable accounting contract
X402BudgetTracker requires BudgetConfig with {scope:{wallet,chainId,asset},globalDailyLimit,globalPerRequestMax,serviceBudgets,durableDirectory}. The directory must already exist, have a canonical absolute symlink-free path, owner-only permissions and correct process owner. Paths are trusted owner configuration, never derived from remote requests. File names are fixed, ledger files are owner-only regular files opened without following symlinks, sizes are capped, and corrupt/inconsistent ledgers fail closed. A durable initialization marker makes a missing previously initialized ledger fail closed instead of resetting its counters; removing or corrupting either file requires independent operator recovery. mkdir locking plus fsynced atomic rename serializes clients/processes. Never remove a lock based on age: a crashed holder requires independent operator recovery after establishing no writer remains.

reserve(service, amount, binding?) synchronously commits an allowance claim. Payment bindings persist confirmations/proofExpiresAt and retain request-ID replay protection through the original proof deadline. markSubmitting(id) precedes executing the wallet; markSubmitted(id, txHash) persists any known submission hash through the execution callback. release(id) only works before submission. complete(id,log) consumes a submitted reservation once and adds persistent daily totals. A proof-only retry may confirm and complete that same reservation; it creates no new spending claim. Queued, reverted, interrupted and uncertain outcomes stay charged across day changes; no automatic reset, refund, or transaction retry exists. getReservations returns immutable bound pending detail for independent reconciliation. Completed histories are capped at 1000, totals remain independent of history truncation, pending reservations/requests/scopes/files are bounded and capacity exhaustion denies. All public history snapshots are frozen.

MemoryBudgetStore is an explicitly non-durable test alternative and must be shared across test clients. Production isolation must protect the ledger from deletion/rollback and keep agents from configuring larger limits or replacing stores. This accounting is supplemental to owner-configured on-chain AgentVault limits; local files controlled by an agent are not an independent financial boundary.
