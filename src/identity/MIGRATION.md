# v5 identity, trust and staking migration

Credentials now use a custom `AgentWalletEd25519EnvelopeV1` JSON signature. They are not W3C Ed25519Signature2020 credentials. Reissue v4 credentials; body-only signatures are rejected. `verifyCredentialSignature(credential,{expectedIssuer,expectedSubject,now})` verifies signed proof semantics and expiry, never economic claims. `verifyCredential` is a deprecated alias for signature-only verification.

`ERC8004Client({chain,registryAddress,rpcUrl})` requires an explicit verified registry address and trusted RPC URL. There are no default deployments. Registration uses ERC-8004 `register(string)` or `register(string,(string,bytes)[])` overloads and returns a successful receipt plus decoded agent ID. HTTPS metadata is restricted to public addresses with pinned DNS, TLS hostname validation and bounded retrieval; inline JSON must be a bounded base64 data URI. IPFS resolution requires a separately configured trusted public HTTPS gateway.

`new AgentStakingPool({token,aToken})` uses owner-verified AAVE deployments. Call `deposit({wallet,amount})`, `withdraw({wallet,amount})` and `getBalance(wallet)` with a guarded `AgentWallet`. Amounts are bigint base units. Writes return `{txHash,receipt}` after confirmed execution. AAVE withdrawals remain in the vault. The SDK charges no fee. Balances are one-block actual aToken and vault principal reads, including yield and principal shortfall. Remove raw `walletClient`, `agentDID`, `amountUsdc`, presumed APY and fee collector integrations.

`verifyAgent` takes explicit `{publicClient,walletAddress,chainId,expectedCodeHash,token,aToken,privateKey,ownerSignature,challenge,expiresAt}`. The owner signs the exact `walletBindingMessage({did,walletAddress,chainId,challenge,expiresAt:ISO_DATE})`; this signature binds the agent DID to owner authority on that chain. Do not use the agent key as evidence of vault ownership.

`await verifyTrustBundle(bundle,{publicClient,walletAddress,chainId,expectedCodeHash,token,aToken,expectedIssuer,expectedChallenge})` rechecks the signed block and independent on-chain facts using verifier-owned trusted configuration. Use a fresh challenge for each authorization and consume it atomically in your application. `verifyTrustBundleSignature` authenticates only the claim signature. Neither API estimates wallet age or generates reputation/task scores. RPC, vault code and AAVE deployment authenticity must be established independently by the verifier; these tests do not establish a live-chain audit.
